# Memory summarizes finished Sessions into one Memory Summary

Users found Memory impractical: it only grew, and keeping it useful was their job. On one heavy user's computer (2026-10-03 to 10-27) it held 1,028 entries in 339k characters after 24 days. Droid called `memory_add` 1,054 times against 114 `memory_replace` and 43 `memory_remove`. `insight` entries, mostly the story of one task, took 52% of the characters; 36% of the entries had never been returned by a search, and 24% of 751 searches found nothing. The largest Project Memory (352 entries, 123k characters) had never been consolidated and would reach ADR 0010's hard limit, where writes are refused, in about five weeks. Consolidation was a button that corner cards asked the user to press, and topics (ADR 0030) only moved the problem.

Codex (`openai/codex`, `codex-rs/memories`, memory v2) and oh-my-pi's `local` backend, a port of it, need no upkeep: a background job summarizes each finished Session from its transcript, and a second step folds the summaries into one short summary that every Session starts with. The model in a Session writes only when the user asks it to remember something.

We move Droi's Memory to Codex's memory v2, kept in plain files:

- **One Memory folder per computer** (`<user data>/memory/`, beside the old files), with no Project / Global split, no topics, no categories and no size limits for the user to manage:
  - `memory_summary.md`, the **Memory Summary**: first line `v1`, then `## User Profile`, `## User preferences`, `## General Tips` and `## What's in Memory`, under 10,000 bytes. Its last section groups recent work by project and points to Session Summaries.
  - `session_summaries/<last change>-<session id prefix>-<slug>.md`, one **Session Summary** per summarized Session, at most 9,000 bytes, with a header (session id, last change, Workspace, title).
  - `notes/<time>-<slug>.md`, the **Memory Notes**. Droi never deletes one.
  - `state.json`, the Host's bookkeeping: which Sessions were summarized at which modification time, each Session Summary's reads, the inputs the Memory Summary took in (by SHA-256), the last failure and the latest 40 Memory Sessions.
  - `started/<session id>.json`, written by the hook, and `reads.jsonl`, appended by the Memory Server; the Host folds both into `state.json`. Each file has one writer, so no process needs a lock on another's.
  - `session-summary-prompt.md` and `memory-summary-prompt.md`: Codex's prompts, adapted, copied for the user to edit as before.
- **The SessionStart hook** (startup, clear, compact) records the Session, so only Sessions of Droi's own Daemon with Memory on are ever summarized. It injects a short read policy, the Memory Summary and the Memory Notes the Memory Summary has not taken in yet (newest first, within 3,000 characters). The policy says to read a Memory Note the summary points to before work in that project, and a Session Summary only when it could change the answer. The `UserPromptSubmit`, `PreCompact` and `SessionEnd` hooks are gone.
- **The Memory Server** offers `memory_search` (words across the folder, answered as `file:line`), `memory_read` (one file of the folder by its path; a path outside it is refused; reading a Session Summary counts as a use), `memory_list` and `memory_note`. Droid calls `memory_note` only when the user explicitly asks it to remember, forget or correct something; a note over 4,000 characters or holding a secret is refused. Everything else Memory knows comes from transcripts after the fact.
- **Session Summaries** (Codex's phase 1). The Host looks for work when Memory starts, every 15 minutes, soon after a new Memory Note and when the Daemon comes back, one pass at a time. A Session qualifies when the hook recorded it; it is not a Memory Session, a subagent, an Automation run, a `droid exec` or a mission worker; its transcript changed within 30 days but not in the last 6 hours; and it was not summarized at that modification time. A pass takes at most 16, newest first, 4 at a time. The input is the user's prompts, Droid's replies, compaction summaries and one line per tool call, tool result and notice from the Daemon, within 80,000 characters: those single lines go first when it is too long, then compaction summaries, then replies. A notice is a message the Daemon puts in the user's turn, such as a finished background task, an interruption or an error; it carries a `visibility` that the user's own prompts never have, and it is shown as a notice so that the summary does not take it for the user's words. The answer is `{summary, slug}`, empty when nothing is worth keeping. Secrets are redacted by pattern from the conversation before it is sent and from the answer. A Session that goes on is summarized again and its file replaced. A failure is tried again after one hour, then after two; after three, the Session waits until it changes. A Memory Session the Daemon could not start, as when it already runs all the Sessions it can, or lost when it went away, as when the Host restarts it for another droid, is tried again an hour later without counting as a failure.
- **Selection** follows Codex: the Memory Summary draws on at most 256 Session Summaries, the most read first, then the most recent. One not read for 30 days (or never read and written 30 days ago) is deleted, and the Memory Summary loses what only it supported.
- **The Memory Summary** (Codex's phase 2) is one structured-output Memory Session per batch, not an agent editing files. When its inputs (the selected Session Summaries and every Memory Note) differ from what it last took in, a Memory Session at medium reasoning effort gets the current summary, the changed files (notes first, then summaries oldest first, at most 40,000 characters a batch) and the removed ones, and answers the whole new summary as JSON. Each batch is told the current summary's size and the limit, in bytes. An answer whose only fault is its size goes to one more Memory Session, which shortens it to under 7,000 bytes: models misjudge bytes, Chinese text most of all, and the same batch would come out too long at every retry. Some models ignore the size even then, so a shortened answer still too long is cut by whole lines of `## What's in Memory`: its Session Summary pointers go first, the last first, down to 7,000 bytes; only when none is left do its last lines go, and only down to the limit, since they may hold what came from a note. An answer that does not start with `v1`, lacks a heading, or whose sections before `## What's in Memory` alone reach the limit is rejected: the current summary stays, and the update is tried again an hour later. A batch lost because the Daemon went away is no fault of the batch: the pass the Daemon's return starts tries it again at once, but only once, so a Daemon that keeps going away waits the hour too. Each batch's answer is saved before the next batch goes out. Memory Notes win over everything else, and none may be lost: a note that holds across projects is kept in the summary in few words, and a note about one project keeps its main claims under that project with a pointer to the note file. Room is made by dropping Session Summary pointers, never what came from a note. Without that rule, every model tried kept only about half of the user's earlier corrections after the import, and one dropped the company's name.
- **The earlier Memory is imported once.** `memory.sqlite` is opened read-only and left in place, so an older Droi still finds it. Each earlier Memory's corrections and preferences, which the user gave, become Memory Notes; its other entries become Session Summaries of their own, dated by their newest entry, which age out like any other unless read.
- **Two models** in Settings → Memory, both read at each Memory Session so no restart is needed: the Session summary model (low reasoning effort) and the Memory Summary model, which is the first until picked.
- **Memory Sessions can be opened.** They are still tagged `droi.memory`, kept out of every session list and archived after their turn (ADR 0011). They now start with no tool but their structured answer (`restrictToolIds`): asked not to, gemini-3.8-flash still tried to count bytes with Script and Execute, and the refused call ended its turn. And they are now closed: an open Session keeps its place in the Daemon, which runs only so many at once, so a pass of Memory Sessions left open would keep the user's own Sessions from starting. Settings → Memory lists the latest with their model, time and failure, and opens any of them in the Session view. The model shown is the one the Daemon reports for the Session: given a model id it does not know, the Daemon runs its default instead without an error (asked for `claude-haiku-5.5`, it ran `gpt-6-sol`).

Settings → Memory shows the Memory Summary's size and time, how many Session Summaries and Memory Notes there are, how many Sessions wait, and the last failure. **Update now** takes the Sessions left for 10 minutes and updates the Memory Summary, even before a retry is due. The consolidate buttons, the size rows and both corner cards are gone.

## The default model

Both Memory models default to `claude-haiku-5-5`. We compared four models on the same material: 8 of the user's real Sessions (from a one-line question to 82,000 characters of conversation, Chinese and English, with background-task notices, interruptions and two pasted credentials) and the import of the user's 1,029 earlier entries (339k characters, 11 batches).

- **gemini-3.8-flash** wrote half of the Session Summaries of a user who writes Chinese in English, and stated Droid's web findings as confirmed. Updating the Memory Summary at medium effort, one batch passed the 10-minute limit; the import did not finish in 21 minutes.
- **deepseek-v4.1-flash** wrote the most detail but ran into the 9,000-byte cut in half of its Session Summaries, which drops the end, and its first Memory Summary batch ended after 7 minutes without a structured answer.
- **gpt-6-luna** was the fastest (the import took 7.5 minutes). Its Session Summaries were short, it once wrote the Memory Summary in English and marked a claim `[note]` with no note behind it, and after the import it kept 9 of 15 checked corrections, dropped the company's name, and pointed to 3 files that do not exist.
- **claude-haiku-5-5** wrote the Session Summaries a later Session can act on (final state, open questions, exact identifiers, what was verified and what was not), and after the import kept 14 of 15 checked corrections with no invented file name. The import took 13 minutes. It costs the same as gpt-6-luna and less than `glm-5.3-flash`, the earlier default, whose Session Summary in the first live test ended without a structured answer.

No model kept a Memory Summary under its size on its own once the import had filled it, so with this user's 101 earlier corrections and preferences each later update is followed by a shorten Memory Session and, usually, the cut of older Session Summary pointers.
## Considered Options

- **Keep Droid writing entries in the Session, and consolidate automatically.** Rejected: ADR 0010 chose the model in the conversation because it knows why something happened and can fix a stale entry, but the data shows it adds seven times as often as it fixes, and an automatic consolidation still has to read a store that grows without bound. A summary written after the Session sees all of it, and only one file has to stay small.
- **Codex's phase 2 as it is: an agent that edits the Memory folder, with a git baseline to diff against.** Rejected: its only output in v2 is one file under 10,000 bytes, so a JSON answer holding that file gives the same result without write access, tools or git in a Memory Session (ADR 0011 keeps them tool-free). The changed and removed files are found by hash instead of by git.
- **Keep SQLite for the pipeline's state, as Codex does.** Rejected: Codex needs leases because many Codex processes start the pipeline at once. One Host runs Memory work on a computer, so an in-process lock and `state.json` are enough.
- **Keep a search index.** Rejected: Codex v2 has none, and a few hundred small Markdown files are read in milliseconds.
- **Keep Project and Global Memory.** Rejected: a Session's folder is only a hint about its work, a chat without a project had nowhere good to write, and the Memory Summary already groups work by project.
- **Move `memory.sqlite` aside after the import.** Rejected: going back to an older Droi would then find no Memory.

## Consequences

- What a Session teaches reaches later Sessions only once it has been left for 6 hours, or after Update now. A Memory Note reaches the next Session at once, beside the Memory Summary, until the Memory Summary takes it in.
- Every qualifying Session costs one Memory Session, and the Memory Summary one per batch when something changed; when nothing changed there is no model call.
- Memory no longer refuses a write or asks the user to tidy it: the Memory Summary has a fixed size, and unused Session Summaries age out.
- Only Sessions the hook recorded are summarized: those on Droi's Daemon while Memory is on, never the droid CLI's. Sessions from before the update are summarized only if they run again.
- Session Summaries and the Memory Summary are model output: secrets are redacted by pattern, and the prompts tell the model to treat transcripts and notes as evidence, never as instructions.
- The earlier Memory's files (`memory.sqlite`, its Markdown copies and its prompts) stay in the folder, unused.
- This supersedes ADR 0030, and in ADR 0010 the store, the scopes, the categories, the size limits, Droid's own writes and every hook but SessionStart. ADR 0010's attachment through the Runtime Overlay and the Memory switch, and ADR 0011's Memory Sessions, stand.
